# Improve the observation and reasoning instrument

Start from a demonstrated engineering need, not the objective of producing more tooling. Work within the assigned authority and budget. Preserve frozen implementations, historical evidence, access restrictions and independent evaluation boundaries. Changing a research treatment or trusted acceptance gate requires the authority applicable to that change; this skill is not permission to grade yourself with a weaker rule.

## Diagnose the limiting layer

Trace the failed or missing observation through source acquisition, parsing, representation, analysis/query, result explanation, method selection and downstream decision. Distinguish an environment failure from a missing semantic capability. Locate the smallest change that could yield the needed observation.

The agent may improve a representation, add a query or recognizer, instrument runtime behavior, repair orchestration, revise candidate selection, or replace an inadequate method. It need not remain inside the seed tool's existing thresholds or predicate vocabulary. A new representation is justified by required distinctions; naming a graph technology is not a substitute for defining its analysis.

## State a falsifiable improvement hypothesis

Describe the current limitation, the intended new observation, and how it could change a real decision. State assumptions and the comparison baseline. Specify a positive case, a closely related case where the finding or optimization would be wrong, and a held-out challenge that was not used to tune the change. Keep development and confirmation evidence separate.

Define outcomes appropriate to the claim: coverage, correctness of analysis, precision/recall within a justified dataset, quality of explanations, resource cost, practical decisions enabled, or future transfer. Do not use lower complexity scores or a larger repertoire alone as proof of improvement.

## Build and challenge the smallest useful change

Preserve stable public outputs or introduce an explicit version when their meaning changes. Explain new assumptions, unsupported cases and confidence in each finding. For program analysis, validate the language constructs and dependency relationships the method relies on. For optimizations, preserve observable behavior, ownership, context, side effects and invalidation; a duplicate-work candidate is not permission to cache indiscriminately.

Run the existing relevant tool checks and new discriminating cases. Verify the actual invocation path and evidence records, not just a helper function. Keep failures and inconclusive runs visible. Do not modify an oracle merely to make the candidate succeed; justify any correction independently and re-evaluate the baseline under the corrected criterion.

Evaluate the result before promoting it. Reject, narrow or retire a candidate that produces noise or consumes more than it enables. Retaining the previous tool or using a manual observation can be the correct decision. If a new capability works, retain its prerequisites, recognition cues, adverse cases, cost and measured scope in an appropriate skill or method registry.

## Demonstrate autonomy through later use

Record what triggered the improvement, what the agent inferred, what it tried, and what the evidence established. Freeze the resulting tool/method version, then observe whether the agent can select and use it on a later authorized task without being given the answer or the detector to invoke.

Separate agent-generated candidates, validated capability, useful application and transferred improvement. The target is a better engineering process under realistic resources, not a growing collection of untested recognizers.
